# Opus 작업 지시 — 주식 플랫폼 점검 후 수정

아래 내용을 같은 저장소의 Opus 작업에 전달한다.

---

주식 플랫폼 감사 결과를 검증하고 필요한 수정을 구현해줘.

먼저 루트 `AGENTS.md`, `CLAUDE.md`, `docs/AUDIT_2026-09-17_STOCK_PLATFORM.md`를 읽고 현재 코드와 대조해. 감사 기준 커밋은 `d00eb7048105e10c0e34632e688cdf254ba75c54`이며 그 이후 변경이 있으면 현재 코드를 우선해. 감사 문서의 주장을 그대로 믿지 말고 실제 호출 경로와 재현 테스트로 확인해.

요구 결과는 수정 코드, 수정 전 실패하는 회귀 테스트, 변경 후 검증 결과, 남은 운영 확인 사항이다. 점검 계획만 답하고 끝내지 말고, 아래 범위의 수정과 검증을 완료해. 기존 사용자 변경을 덮어쓰지 마.

## 공통 원칙

- 각 버그는 실제 서비스/응답 경로를 타는 재현 테스트를 먼저 작성해 실패를 확인한 뒤 고쳐. 구현 소스를 문자열로 검색하는 테스트만으로 동작 검증을 대신하지 마.
- 점수 분모 80, validCount≥3, 75/55 임계, 수급 캡, 과열 페널티, 거래정지 게이트의 기존 fail-open 의미는 유지해. 결론 표시의 잘못된 BUY 분류는 아래 F6 범위에서만 바로잡아.
- 시세는 공용 `StockPriceService` 경로를 유지해. `warnIfPriceOutlier`는 로그 전용이며 가격 보정 금지.
- KRX 봇/정규장과 NXT 표시 시간 경계를 합치지 마.
- 결측·조회 실패·노후 데이터를 0/정상/안전/미충족 값으로 숨기지 마. 상태와 기준일을 함께 전달해.
- 봇 정책 변경, 주문 취소/정정 API 추가, 운영 DB 보정·삭제, 실전 주문 테스트, 배포·푸시는 이 요청에 포함하지 않아.
- 실전 매도 UNKNOWN의 기존 정책, 재시작 잔고 대조의 경고 전용 정책, 일일손실 브레이커의 ‘신규 진입만 차단’ 원칙을 보존해.
- F1 주문 정합성과 F2/F3/F4/F5/F6 표시·평가 변경은 독립적으로 검토 가능한 변경 단위로 만들어. 요청 범위 밖 리팩토링은 하지 마.

## 1. F2 — D+3 평가의 확정 거래일 경계부터 수정

대상: `SignalD3EvaluationService`, `SignalD3Evaluator`, `SignalOutcomeController`, 관련 테스트.

문제: `run()`은 D+3 날짜가 오늘이면 시간과 무관하게 평가한다. 수동 백필에서 오늘의 장중 봉을 OK로 저장할 수 있고, 기동 장전 실행에서는 미도래 행을 MISSING_BARS로 만들어 7일 뒤로 밀 수 있다.

요구 동작:

1. 주입된 Clock과 거래일 달력으로 ‘현재까지 마감된 마지막 평가 가능 거래일’을 공통 판정해. 시계 판정은 서비스 계층에 두고 평가 순수함수의 결정성을 유지해.
2. D+3이 아직 마감되지 않은 행은 저장하지 말고 미도래로 남겨. `MISSING_BARS`/`NO_INDEX` 등 실패 이력을 쓰지 마.
3. D+3이 과거 확정 거래일인 행은 장중에도 처리 가능하게 해. 전체 백필을 장중이라는 이유로 차단하지 마.
4. 크론·기동 따라잡기·수동 실행·force에서 동일한 경계가 적용돼야 해. dryRun 보고도 일관되게 해.
5. D+3 세 날짜 고정, 응답 봉만 사용, OK 외 수익 필드 null, 구 평가 컬럼 보존 및 재시도 공정성은 유지해.

필수 재현: 9/14 기록 → 9/17이 D+3인 행, 9/17 장전/10:00/마감 경계/장후. 장중 봉이 응답에 있어도 확정 저장하지 않는지 확인해. 주말/연휴, 과거 창, 재시도 및 force도 검증해. 임계 시각은 기존 KRX 경계를 근거로 정하고 NXT 20시로 바꾸지 마.

## 2. F3 — 정상 0% 보합을 보존

대상: `StockPriceService.fetchFromKoreaInvestment`, `fetchStockPrice`, `fetchYesterdayChangeRateFromDaily`, `supplementFromNaver`, 관련 테스트.

문제: 현재 등락률과 전일대비가 0이어도 결측으로 취급해 일봉/네이버 값으로 덮는다. 현재가는 유지되어 DTO 내부의 시점과 값이 어긋난다.

요구 동작:

1. 유효한 숫자 0과 null/파싱 실패를 구별해. 정상 0/0은 폴백으로 덮지 마.
2. 실제 결측의 보충은 같은 기준가격·날짜·시장을 확인할 수 있는 근거가 있을 때만 허용해. 어제 등락률을 현재 등락률로 복사하지 마.
3. 누락된 등락률을 동일 응답의 유효 전일대비로 계산하는 정상 경로는 보존해. 계산 근거가 없으면 null을 유지해.
4. 일봉의 첫 행을 무조건 ‘어제’로 간주하지 마. 원시 현재가를 보정하거나 새 시세 조회 서비스를 만들지 마.

필수 재현: 통합시세 10,000원·0원·0%, 다른 시점의 일봉/네이버 +5%. 반환이 0%인지, 외부값으로 덮지 않는지 검증해. null/null, 한 필드 결측, 장전·장중·NXT 장후, 폴백 실패도 포함해.

## 3. F4/F5 — 결론·체크리스트가 미확인 데이터를 확신으로 표시하지 않도록 수정

대상: `StockConclusionService`, `BuyChecklistService`, 필요한 DTO/조회 메서드, `StockConclusionCard.vue`, 체크리스트 표시 컴포넌트, 관련 테스트.

F4 요구:

- 종목별 과거 스냅샷이 존재한다는 이유로 현재 매수 권고와 오늘 가격 목표가를 만들지 마.
- 거래일 달력과 실제 추천 스냅샷 생성 주기를 보고 현재 판단에 유효한 시점을 정의해. 주말·연휴에는 단순 15분 TTL로 전부 무효화하지 마.
- 노후/거래정지이면 기준일과 사유를 표시하고 현재형 매수 권고·신규 매매계획을 중단해. 과거 이력을 표시한다면 과거라는 점을 명시해.
- 신선한 정상 스냅샷의 기존 매매계획 -3/+5, 타이트 -2/+3은 유지해.
- 보존 기간은 현재 코드의 7일 정리 작업을 확인해. 옛 문서의 30일을 복사하지 마.

F5 요구:

- `isActive=true`가 동기화 전 fail-open인지, 실제 상태 확인 결과인지 구분할 읽기 전용 상태를 제공해. 기존 boolean 게이트의 전역 동작은 유지해.
- 연속매수 `endDate`의 신선도를 확인해. DB 최신일을 현재일로 간주하지 마.
- 공매도 비율에 기준일/가용성 정보를 연결해. 공개 지연·수집 주기를 확인한 뒤 노후 기준을 정해. 수급과 동일한 당일 기준을 무작정 적용하지 마.
- 조회 실패/미확인/노후를 정상 체크 표시로 나타내지 마. `dataMissing`·분모·요약 문구가 서로 일치해야 해. 결측을 새 매수 차단 정책으로 바꾸지 마.

필수 재현: 며칠 전 80점 스냅샷+현재 가격, 최신 추천 후 거래정지, 금요일 정상 스냅샷을 주말/월요일 장전에 조회, 마스터 동기화 전, 정상 동기화 후, 과거 연속매수 endDate, 노후/결측/실측 0 공매도, 각 의존성 예외. 실제 프론트 렌더도 테스트해.

## 4. F6 — 55점 미만 BUY 규칙 정리(잠재 결함)

대상: `StockConclusionService.build`, `StockConclusionServiceTest.supplyStrongButTechnicalWeak`.

수급≥15·기술<8만으로 BUY를 만드는 규칙을 55점 기준과 일치시켜. 총점 50·54에서 BUY 또는 STRONG_BUY가 나오면 안 돼. 필요하면 수급 강세를 관찰 문구로 남겨. 기존 가치 강세 HOLD 분기와 55/75 경계는 보존해.

현재 추천 writer는 55점 이상만 저장하므로 현 운영에서 발생했다고 주장하지 마. 테스트가 50점 BUY를 정상으로 고정하고 있으므로 왜 기대값을 바꿨는지 문서화해. 핵심 추천 산식과 저장 컷을 바꾸지 마.

## 5. F1 — 실전 분할익절 체결 정합성(별도 변경 단위)

대상: `AutoTradingBotService`의 1차 익절/`executeScalpingSell`, `RealTradeService` 체결/이력 처리, 필요한 포지션 상태와 테스트.

먼저 10주 보유에서 5주 익절 주문이 접수됐지만 0주 또는 2주만 체결된 재현을 만들어. 현재 `isPartialSell=true`에서 확인을 건너뛰는지, `halfSold`·5주 매도 이력이 남는지 검증해.

수정 전 상태 전이를 짧게 정리하고 구현해:

- 주문 접수, 실제 체결, 목표 분할익절 완료를 구분해.
- 분할매도에서도 체결을 확인하고, 확인된 NONE/PARTIAL을 전량체결 기록으로 남기지 마.
- **`halfSold=false`만 되돌려 다음 틱에 새 매도를 넣는 수정은 금지.** 기존 주문의 미체결 잔량이 뒤늦게 체결되면 중복 청산이 된다. 주문번호·목표수량·관측 체결 누계·재시작 상태를 고려해 기존 주문을 추적해.
- 기존 미체결 주문이 살아 있을 때 새 주문이 중복 제출되지 않는 테스트를 작성해. 수집 실패 UNKNOWN 처리는 기존 명시적 정책을 유지해.
- 확정 체결 변화가 이력·일일 실현손익에 중복/누락 없이 반영되는지 확인해. 확인된 0주가 확정 수익으로 남으면 안 돼.
- VIRTUAL·전량매도·손절/청산·킬스위치·주문 성공 후 DB 실패 방어를 보존해.
- 취소/정정 API를 새로 호출하거나 실제 주문을 넣어 검증하지 마. 현재 API로 해결할 수 없는 주문 상태가 있으면 그 한계를 숨기지 말고 남겨. 임의의 자동 재주문으로 메우지 마.

필수 테스트: NONE/PARTIAL/FULL/UNKNOWN, 늦은 추가 체결, 반복 조회 멱등성, 다음 틱 중복 주문 방지, 재시작, 이력 저장 실패, 알림, VIRTUAL 회귀. 스키마 변경이 필요하면 기존 행 호환성과 migrationTest를 포함해.

## 검증 및 보고

- 백엔드 변경 후 `./gradlew test` 전체 통과를 확인해. Windows에서는 wrapper를 사용해. `-PskipFrontend`로 실행했다면 프론트 빌드는 별도로 검증해.
- 프론트 변경 후 `npm test`, `npm run build`. Python 변경 시 `pytest`.

- 변경 범위와 diff를 검토하고 테스트 통과 뒤 멈춰. 운영 DB/주문/배포/푸시는 하지 마.
- 최종 보고에는 발견→수정→수정 전 실패→수정 후 통과의 근거, 파일 위치, 남은 운영 검증을 적어. ‘안전해졌다/수익성이 검증됐다’로 과장하지 마.
- `CONTROL_ROOM_FLAGS.md`/백로그는 실제로 해결한 항목만 갱신해. 미해결인데 플래그를 지우지 마.
- V59 게이트의 구값→교정값 전환, REAL 가용현금 필드 교체, 차트 타이밍 추천 승격은 별도 판단 사항으로 남겨.
