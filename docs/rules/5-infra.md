#### §5.5

- **backend 컨테이너 메모리·OOM 처리(2026-09-15 사고)**: 2026-09-11 16:37 `OutOfMemoryError` 가 **Tomcat Acceptor 스레드 하나만 죽였고 JVM 은 살아남았다** — 배치·모닝브리핑·텔레그램은 정상으로 보이는데 **API 만 3.5일간 죽어 있었다**(8080 소켓 LISTEN 1 / CLOSE_WAIT 87, 워커 11개 전부 유휴, 스레드 덤프에 Poller 는 있고 Acceptor 만 없음). 진단 순서가 중요하다 — 컨테이너 `Up (unhealthy)` + 사이트 200(nginx 가 정적만 줌)이면 **JVM 이 아니라 HTTP 수신부만 죽은 것**을 의심하고, `/proc/net/tcp` 의 CLOSE_WAIT 적체와 `kill -3 1` 덤프의 Acceptor 유무를 볼 것(이미지에 `jmap`/`jcmd` 가 없다). ⚠ **RSS % 를 OOM 지표로 쓰지 말 것** — JVM RSS 는 힙 상한까지 자연히 차서 85~97% 가 정상이다. 지표는 `actuator/prometheus` 의 **`jvm_gc_live_data_size_bytes` ÷ `jvm_gc_max_data_size_bytes`**(GC 후 생존량 ÷ 구형세대 상한)다. 근본 원인은 **컨테이너 상한 1536M**: JVM 서버급 판정 임계(1792MB) 아래라 **SerialGC** 가 선택되고 구형세대가 768MiB 로 잘려, live set 이 거기 붙은 채 회수 불가가 됐다(그래서 768 이라는 수치 자체가 "천장에 눌린" 값이지 진짜 작업집합이 아니었다 — 3072M 으로 올리자 G1GC 전환 + 구형세대 2304MiB 에서 live set 148MiB 로 떨어졌다). **1792MB 아래로 되돌리지 말 것.** OOM 대응은 `JAVA_TOOL_OPTIONS` 세 옵션 — `HeapDumpOnOutOfMemoryError` + `HeapDumpPath=/dumps`(**반드시 마운트 경로**, 내부 경로면 재생성 때 증거가 같이 사라진다 — 이번에 그래서 원인을 못 잡았다) + `ExitOnOutOfMemoryError`(**OOM 이면 죽고 `restart: unless-stopped` 가 살린다** — 반쯤 망가진 채 조용히 사는 것보다 낫다. 대가는 장중 OOM 시 재시작이 봇 reconciliation·봉 수집을 끊는 것). 감지는 09:00 헬스체크 크론의 unhealthy 경보가 담당하는데 **9/13·9/14 텔레그램이 갔는데도 3일을 그냥 지나갔다** — 경보는 작동했고 사람이 못 본 쪽이다.

- **배포는 한 번에 하나, 떠 있는 커밋은 라벨로 확인한다(2026-10-06)**: 실행들이 겹치면 둘 다 같은 이미지 태그(`my-server:prod`·`my-python:prod`)에 올리고 서버는 그 태그를 받으므로, 늦게 시작한 실행이 먼저 끝나면 **예전 코드가 마지막에 올라간다**(10/6 14:51·14:55 두 푸시가 병렬로 돌아 백엔드가 15:01·15:06 두 번 재생성 — 그날은 순서가 맞았다). 그래서 deploy.yml 최상위 `concurrency: deploy-main`(진행 중인 실행은 끝까지 두고, 기다리는 실행은 더 새 푸시로 바뀐다 — 각 실행이 그 커밋까지 전부 담으므로 최신 하나만 배포하면 된다). 백엔드·파이썬 이미지에 `org.opencontainers.image.revision=<커밋>` 라벨을 달고, 배포 마지막 단계 'Verify deployed revision' 이 서버 백엔드 라벨을 그 실행의 커밋과 대조해 **다르면 실행을 빨갛게 만든다**(헬스체크 200 은 '무언가 떠 있다'까지만 말한다). 배포 확인은 부팅 로그 문구·번들 문자열로 추측하지 말고 `docker inspect -f '{{ index .Config.Labels "org.opencontainers.image.revision" }}' myplatform-backend` 로 푸시한 커밋과 대조할 것(이 변경 전 이미지는 라벨이 비어 있다).

#### §5.14

- **밖에서 부를 일이 없는 로그인 없는 주소는 nginx 가 막는다(2026-11-10)**: 진단 API(`/api/diagnostics`)와 python API(`/api/v2`)는 로그인 없이 응답하는데 nginx 가 `/api/**` 를 그대로 넘겨 인터넷에서 닿았다. 화면은 둘 다 쓰지 않는다 — 진단은 서버 안에서 `curl localhost:8080/api/diagnostics/…` 로 보고, python 은 백엔드가 도커 내부망(`python-backend:8000`)으로 직접 부른다. 그래서 nginx 가 두 접두 경로를 403 으로 끝낸다(`nginx/default.conf` — 접두 location 은 가장 긴 것이 이겨 일반 `/api/` 프록시보다 먼저 맞는다). 운영과 같은 nginx 1.25 에 실제 설정을 올려, 경로를 비튼 요청(`//`·`%64`·`..`·`;`)까지 403 이고 다른 API·SSE·로그인·화면은 그대로 통하는 것을 확인했다. **밖에서 진단 주소가 403 인 것은 고장이 아니다** — 점검은 서버 안에서 한다. 처음엔 임시 차단이었고, 같은 날 Spring 권한 규칙도 정리했다(바로 아래 항목) — 이 블록은 두 번째 겹으로 남긴다. **이 블록을 지우거나 프록시로 되돌리지 말 것** — 다시 열려면 로그인·권한부터 붙인다. 회귀 `NginxExternalBlockTest`(설정에서 블록이 빠지거나 프록시로 바뀌는 것을 막는다 — 실제 동작은 배포 뒤 바깥 호출로 확인).

#### §5.15

요청**(`InternalCaller` — 연결 주소가 루프백·사설 대역이고 nginx 가 붙이는 `X-Real-IP` 가 없음)은 진단(`/api/diagnostics/**`)·KOSPI 지수 일봉(python 이 토큰 없이 부른다)·측정 메타데이터(시그널 적중률·비교·시계열, 강력가치 빈도, 섹터 강도·차트 타이밍)·액추에이터(health 밖)·API
