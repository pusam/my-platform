#### §4c.19

- **KIS 접근토큰 발급은 분당 1회 — 토큰은 Redis 로 프로세스를 넘긴다(2026-09-11)**: 초과하면 HTTP 403 `EGW00133`("접근토큰 발급 잠시 후 다시 시도하세요"). 토큰이 프로세스 메모리에만 있으면 새 컨테이너는 직전 발급을 몰라 다시 요청한다 — 커밋 2개를 연달아 밀어 컨테이너가 8분 간격으로 두 번 재생성되자 두 번째가 403 을 맞고 **90초간 모든 KIS 호출 불가**(ERROR 11줄; 65초 쿨다운이 재시도해 자가 회복했고 장전이라 매매 영향은 없었다). 그래서 `KisTokenManager` 가 발급분을 Redis(`kis:access-token`, 값 = `{token,expireAt}` JSON + 남은 유효기간을 TTL)에 게시하고, 로컬 캐시가 비면 **쿨다운 판정보다 먼저** 거기서 채택한다 — 403 으로 쿨다운에 걸린 프로세스도 유효 공유 토큰이 있으면 65초를 기다릴 이유가 없다. 유효 창은 로컬과 같은 `isUsable`(만료 1h 전) **단일 판정**이라 곧 만료될 토큰을 물고 오지 않는다. ⚠ **무효화는 Redis 도 지운다(`evictFromRedis`) — 이게 빠지면 이 기능이 사고가 된다**: 죽은 토큰이 재시작을 넘어 되살아나 위 EGW00123 20분 전멸이 **영구화**된다. CAS 불일치(이미 재발급됨)면 로컬·Redis 둘 다 안 건드린다. Redis 미구성/장애는 **정확히 종전 동작**(메모리 전용, 모든 접근 best-effort try/catch) — 인증이 Redis 에 인질로 잡히면 안 된다(`SchedulerLockService` 와 같은 fail-open). 삭제가 무조건인 것은 **단일 인스턴스 전제**(§5) 때문 — 멀티 인스턴스로 가면 "값이 같을 때만 삭제"(Lua CAS)가 필요하다(무조건 삭제의 최악은 재발급 1회로 회복 가능, 반대 방향은 회복 불가라 안전한 쪽을 택했다). Redis 에 베어러 토큰을 두는 것은 JWT refresh 토큰(§6)과 같은 신뢰 경계다. 회귀 `KisTokenRedisSharingTest` — 채택·쿨다운회복·삭제를 각각 끄면 정확히 그 3건이 실패한다.

#### §4c.32

- **KIS 일봉의 '그날' 행은 다음 날 아침에야 KRX 종가다 — 저녁 값을 종가로 쓰지 말 것(2026-11-04, 야후·네이버 외부 대조로 발견)**: 시장 코드가 J(KRX)여도 그날 행의 종가·거래량은 장 마감 뒤 저녁 내내 바뀌고 다음 날 KRX 종가가 된다. 11/3 삼성전자: 15:39 통합 시세·KIS 마스터 기준가·야후·네이버 '전일'·다음 날 받은 봉 = 219,500 / 그날 저녁 저장 봉 = 222,000 (삼성전기 1,105,000 vs 1,122,000, 현대차 277,500 vs 278,500, 014710 은 9,400 vs 9,110 · 거래량 1,663 vs 969). 저녁 값의 정체는 확정 못 했다 — 그 시각 통합 시세와도 다르다(18:30 SK하이닉스 통합 1,407,000 vs 봉 1,414,000). 'J 는 KRX 단독이라 18:30 이면 확정'이라던 옛 주석이 틀렸다. **영향 ① D+3**: 그날 19:45 에 평가해 'D+3 KRX 종가'가 저녁 값이었다 — 10/12~11/2 OK 756행 중 86% 가 확정 봉과 달랐고(날짜별 평균 오차 0.33~1.41%, 최대 6.96%) 수익 부호가 뒤집힌 행 39건, 평균 수익 −3.06% vs 실제 −2.82%. 비교 대상 KOSPI 는 15:30 종가라 초과수익에 저녁 움직임이 섞였고, OK 는 다시 재지 않아 그대로 굳었다. → 평가 경계를 `SignalD3EvaluationService.lastFinalTradingDay`(마감 + 16시간 20분 = **다음 날 08:00**)로 — 크론은 그대로라 **D+3 평가가 하루 늦어져 D+4 19:45 에 나온다**. **영향 ② 장중 채점**: 11:30·14:00·17:00 기술 채점·섹터 점수가 저녁 값을 '전일 종가'로 읽었다(다음 날 18:30 에야 바뀌었고 후보 풀에서 빠지면 그대로 남았다) → `DailyBarRefreshService.refreshBarsBeforeOpen`(장이 열리는 날 07:40:30, 후보 풀 ∪ 전 거래일 봉 보유 종목, 약 6분). 07:40 근거: KIS 종목마스터가 07:35 에 전일 최종 기준가·거래량을 담아 나오고, 다음 날 09:00 저장 봉은 실측으로 전부 KRX 종가였다(07:40 도 11/6 첫 회차로 확인 — 754종목 재수집 약 6분 30초, 값이 달라 고친 봉 743개, 삼성전자·SK하이닉스·NAVER·대덕전자 종가·거래량이 야후 KRX 값과 일치. 재수집 종목의 10% 미만이면 WARN). **추천 입력 변경**(기술 축·섹터 등락률) — 표본 시작 전 배포 전제. 저장 경계 `lastSettledTradingDay`(15:40+30분)는 그대로다 — 20:05 계산이 그날 봉을 봐야 한다. 그래서 **20:05 마감 스냅샷의 마지막 봉은 저녁 값**이고(시그널 기록 안 함, 다음 날 08~09시 표시뿐 — 인지된 한계) 패턴 감지(20:20) `close_at_detection` 도 저녁 값이다. 주말·연휴엔 아침 갱신이 안 돌아 그동안 화면의 마지막 봉은 저녁 값이다. 옛 D+3 행은 다시 재지 않았다 — 현재 산식 표본 전이라 참고치다(다시 재려면 관리자 `POST …/d3/backfill?force=true`, 실행당 500종목). ⚠ **외부 대조 함정**: 네이버 `…/api/stock/{code}/price` 일별 표의 종가는 KRX 종가가 아니다(11/3 삼성전자 222,000 — 19:50 통합 시세와 같아 NXT 마지막 값으로 보인다, 1건 확인). KRX 종가 대조는 야후 `{code}.KS` 또는 네이버 `integration` 의 `lastClosePrice`. 통합시세(UN) 전일 대비도 KRX 종가 기준으로 우리·네이버가 같다(−4,750 · −2.16% 일치). 회귀 `SignalD3TradingDayBoundaryTest`·`DailyBarMorningRefreshTest`.
