## 2. 수능일(11/19) 리허설

상태: 완료(e459dc37, 2026-11-10)

2026-11-19(수능일)은 장이 늦게 열리고 늦게 닫힌다. 그날 우리 크론과 판정이 무엇을 하는지 전부 따져서, 틀린 값을 '그날 확정치'로 저장하는 곳을 11/17 까지 고쳐 줘.

확인된 사실:

- 그날 KRX 정규장 10:00~16:30, 종가매매 16:40~17:00. 넥스트레이드는 프리마켓 없음, 메인 10:00~16:20, 애프터 16:30~20:00(CLAUDE.md '장이 늦게 열리고 늦게 닫히는 날').
- `MarketCalendarService` 의 `SHIFTED_SESSIONS` 표와 `marketOpenOf`, `marketCloseOf`, `closesLate` 를 쓰는 곳은 7개 파일이다. 그 밖에 `LocalTime.of(9, 0)`, `(15, 30)`, `(15, 40)`, `(15, 20)`, `(15, 50)` 같은 시각이 10개 안팎 파일에 박혀 있다.
- `@Scheduled` 는 105개다. 평소 '장 마감 뒤'로 잡은 크론 중 15:38(재무 수집, 그 시각 주가로 PER·PBR 을 만든다), 15:40, 15:55, 16:00, 16:05 가 그날은 장중에 돈다. 섹터 3분 수집 크론은 9~15시라 그날 09:00~10:00 엔 장이 없고 16:00~16:30 은 빠진다.
- 이미 달력을 따르는 것: `lastClosedTradingDay`, `isRegularSession`, `InvestorDailyConfirmation`, `MarketBreadth.countsSettled`, 지수 세션, 종목 상세 장전 경계. 15:50·16:00 수급 수집은 건너뛰고 18:00 이 받으며, 등락 수는 16:45 회차가 저장한다.

할 일:

1. 표를 만든다: 크론·판정마다 '11/19 에 실제로 무슨 일이 일어나는가'와 결과(문제 없음 / 틀린 값을 저장 / 표시만 틀림).
2. 틀린 값을 저장하는 경로는 `Clock` 을 2026-11-19 로 고정한 재현 테스트(고치기 전 실패)부터 쓰고 고친다. 크론 시각은 바꾸지 않고 판정만 달력을 따르게 한다(지금까지의 방식).
3. 표시만 틀리는 곳은 고치지 말고 목록으로 알려 줘.

주의: 봇은 꺼져 있으니 봇 상수는 건드리지 않는다. 16:15 수급 확정치 회차는 KIS 가 그날 그 API 를 몇 시에 여는지 모른다. 추측해서 시각을 바꾸지 말고, 실패하면 18:10 회차가 받는지만 확인한다. 추천 입력이 달라지는 수정이면 그렇게 표시해 줘(표본 경계).

## 3. 외부 공개 수치와 자동 대조

상태: 구현(2026-11-11, 브랜치 claude/ext-crosscheck-4e5315) — 설계안 B안(종가 판정·EPS·BPS 기록만), 독립 검토 대기

우리 DB 값을 외부 공개 수치와 매일 자동으로 대조하는 점검을 만들어 줘. 추천·봇에는 넣지 않는 측정 전용이다.

왜: 2026년 가을 가장 큰 데이터 오류는 전부 사람이 네이버·야후 수치와 손으로 대조해서 찾았다. 저녁에 받은 일봉이 KRX 종가가 아니었던 것(D+3 평가 행의 86%가 달랐다), 지주사 PER 이 2~4배 싸 보이던 것, 투자자 순위가 14:30 가집계였던 것, DART 외화 금액. 내부 테스트로는 하나도 안 보였다.

이미 있는 것:

- `NaverConsensusService` 가 `m.stock.naver.com/api/stock/{code}/integration` 을 부른다(1시간 캐시, 실패는 캐시 안 함). 같은 응답의 `lastClosePrice` 가 KRX 종가다. PER·PBR 칸이 있는지는 확인되지 않았으니 응답을 직접 볼 것.
- 네이버 일별 시세 표의 종가는 KRX 종가가 아니다(CLAUDE.md 'KIS 일봉의 그날 행' 항목의 외부 대조 함정).
- 관제실 이상 점검은 `DataAnomalyRules` 의 결정적 규칙이다. 정상이면 조용하고, 걸리면 무엇을 확인할지까지 말한다.

원하는 것:

- 하루 한 번, 아침 봉 재수집(07:40)이 끝난 뒤, 작은 표본(그날 종합추천 후보, 보유 종목, 시가총액 상위 몇 개)의 마지막 확정 봉 종가를 외부 값과 견준다. 종가는 정확히 같아야 한다.
- PER·PBR 은 정의가 달라(우리는 지배주주 최근 4분기) 허용 폭이 필요하다. 폭의 근거를 실제 분포로 대고, 못 대면 종가만 먼저 한다.
- 결과를 표에 남겨 추이를 보고, 어긋남은 관제실 규칙으로 올린다.

지킬 것: 대조 실패는 '일치'가 아니라 '대조 못 함'이다. 어긋나도 값을 고치지 않는다(§3). 호출은 적게, 간격을 두고, 봇 차단을 우회하는 헤더는 붙이지 않는다. 표를 만들면 Flyway 마이그레이션과 `FlywayMigrationTest` 를 같이 고친다.

진행: 새 외부 호출 크론이므로 먼저 설계안(무엇을, 몇 종목, 언제, 허용 폭)만 보여 주고 사용자 확인을 받은 뒤 구현한다.

## 4. 장중 배포 가드와 재시작 기록

상태: 완료(b919af9b·73211976·cdff5fbb, 2026-11-10) — 확인 절차·설계안 C 는 `docs/DEPLOY_GUARD.md`

장중에 실수로 배포돼 백엔드가 재시작되는 일을 막고, 재시작이 언제 있었는지 기록으로 남겨 줘.

왜: main 에 푸시하면 자동 배포되고 백엔드가 재시작된다. 추천 성적의 표본 시작일은 '08:30~15:50 에 재시작이 없던 거래일'이어야 하고(CLAUDE.md §7 표본 시작일), 재무 수집(08:30~09:12, 15:38~16:11)과 16:15 수급 확정치 수집 중에도 재시작하면 안 된다. 지금은 사람이 시계를 보고 지킨다. 2026년 가을 장중 푸시로 표본 시작일이 네 번 밀렸다(10/2, 10/6, 11/4, 11/9).

확인된 사실:

- `.github/workflows/deploy.yml` 은 push(main)마다 테스트, 이미지 빌드, 서버에서 backend·python-backend 를 `--force-recreate` 하는 순서로 돈다. 시각 확인이 없다. 화면만 바뀐 푸시도 백엔드를 재시작한다.
- 장중 재시작 여부는 `docker inspect` 의 StartedAt 을 손으로 본다. 백엔드엔 `ServerStartupListener` 가 있다.

원하는 것:

- A. 배포 가드: 평일 08:20~16:25(KST)에 들어온 푸시는 명시적 표시(예: 커밋 메시지의 `[deploy-now]`)가 없으면 백엔드를 재시작하지 않는다. 테스트와 빌드는 바로 돈다. 미뤄진 배포가 잊히지 않아야 한다(창이 끝난 뒤 자동 배포하거나, 무엇을 하면 되는지 분명히 알리거나. 방법은 골라서 이유를 적어 줘). 한국 휴장일은 워크플로가 몰라도 된다. 기존 `concurrency` 와 'Verify deployed revision' 단계는 유지한다. 시각 판정은 스크립트로 빼서 경계 시각 표로 테스트한다.
- B. 재시작 기록: 부팅 시각을 재시작해도 남는 곳에 쌓고, 관제실에서 '오늘 08:30~15:50 재시작: 없음 / 있음(시각)'과 마지막 장중 재시작 날짜를 보여 준다. 읽기 전용이다(§7).
- C. (설계안만) 화면만 바뀐 푸시는 백엔드를 재시작하지 않게 할 수 있는지, 'Verify deployed revision' 과 어떻게 맞출지.

워크플로 변경은 실제 푸시에서만 검증되니, 무엇을 어떻게 확인할지 적어 줘.

## 5. 서버 감시·백업 보강

상태: 완료(8cd03211, 2026-11-10) — 크론 등록과 외부 사본 장소 고르기는 사용자가 한다(`docs/OPS_WATCH_BACKUP.md`)

서버 감시와 DB 백업을 보강할 스크립트와 설치 안내를 만들어 줘. 서버에는 직접 쓰지 말고(크론 등록은 사용자가 한다) 저장소의 `scripts/` 와 문서만 고친다.

확인된 사실(2026-11-10 서버):

- 크론: 헬스체크는 하루 한 번 09:00(`scripts/server-health-check.sh`, 텔레그램). DB 백업은 매일 03:00 에 `scripts/backup-db.sh` 가 저장한다(29개 약 3.5GB, 1개 약 140MB).
- 9/11~9/15 에 API 가 3.5일 죽어 있었다. 컨테이너는 Up(unhealthy)였고 알림은 9/13, 9/14 에 갔지만 지나쳤다(CLAUDE.md §5).
- 백업은 서버와 같은 디스크에만 있다. 외부 사본이 없고 복구해 본 기록도 없다. 시그널 성적, 장중 수급, 등락 수처럼 다시 받을 수 없는 데이터가 있다.
- `scripts/*.sh` 는 배포 때마다 서버로 복사된다. 디스크는 913GB 중 15% 사용.

원하는 것:

1. 5분마다 돌릴 가벼운 감시 스크립트: 백엔드 상태(도커 health 와 `localhost:8080/api/health`)를 보고, 상태가 바뀐 순간에만 텔레그램을 보낸다(죽음 1회, 계속 죽어 있으면 간격을 둔 재알림, 복구 1회). 자동 재시작은 넣지 않되 넣을 경우의 장단점을 적어 줘. 가짜 curl, docker 로 도는 테스트를 둔다.
2. 백업 외부 사본: 방법 두세 가지를 장단점과 함께 제안한다(서버에 새 비밀값을 두지 않는 쪽 우선, 예: 사용자 PC 가 주기적으로 가져가기).
3. 복구 리허설 스크립트: 최신 덤프를 임시 MariaDB 컨테이너에 복원해 주요 테이블 행 수를 출력한다. 운영 DB 는 건드리지 않는다.
4. docs 에 설치 안내: 사용자가 등록할 crontab 줄을 그대로 적는다.

주의: 토큰은 로그와 출력에 남기지 않는다. crontab 에 비밀값이 평문으로 든 줄이 있으면 파일로 옮기는 방법도 안내에 넣어 줘. `docker system prune --volumes` 는 어디에도 쓰지 않는다.

## 6. 시세 테이블(stock_price) 정리

상태: 완료(89d86362, 2026-11-10) — 보존 잡은 기본 꺼짐, 켜기·기간은 사용자 결정(docs/STOCK_PRICE_RETENTION.md)

시세 캐시 테이블 `stock_price` 가 계속 쌓이기만 한다. 누가 얼마나 옛 행을 읽는지 조사하고, 보존 정책을 만들어 줘. 운영 행 삭제는 사용자가 켤 때만 일어나야 한다.

확인된 사실(2026-11-10 운영):

- 약 399만 행, 484MB(가장 큰 테이블). 2026-01-14 부터 한 번도 지운 적이 없고 하루 약 2만 행(200~240종목)씩 는다. `StockPriceRepository` 주석에도 '무한 증가'라고 적혀 있다.
- 인덱스는 PK 와 (stock_code, fetched_at) 뿐이다. `findTopVolumeStockCodes(since)` 는 fetched_at 만으로 걸러서 전체를 훑는다(`ChartPatternService`, `CompositeSignalService`, `QuantTaService` 가 부른다). `findAllSince` 는 기간 안의 행을 전부 읽는다.
- 저장은 `StockPriceService` 두 곳(save)이다. `batch_job_execution` 은 `BatchJobCleanupService` 가 정리한다(가장 오래된 행이 7일 전).

할 일:

1. 조사 보고: `stock_price` 를 읽는 모든 곳과 각각 며칠 전까지 보는지. 옛 행이 필요한 소비처가 있으면 알려 줘.
2. fetched_at 조회용 인덱스(Flyway). 400만 행에서 부팅 때 인덱스 생성이 얼마나 걸릴지 추정하고, 배포 헬스체크(약 80초) 안에 드는지 적어 줘.
3. 보존 잡: 장이 닫힌 시간에 조금씩 나눠 지운다. 기본은 꺼짐이고(compose 배선과 부팅 WARN 은 CLAUDE.md §4b 방식), 보존 기간은 설정값이다. 기본값 후보는 90일이지만 1번 결과로 근거를 대 줘.
4. 삭제 전에 옛 행을 한 번 파일로 내보내는 방법(사용자가 서버에서 실행할 명령)을 안내에 적는다.

주의: 시세는 단일 경로다(§1). 조회와 저장 경로의 동작을 바꾸지 않는다. 가격 이상치 그물이 쓰는 '종목별 최신 행' 조회가 느려지지 않아야 한다.

## 7. 지침 파일(CLAUDE.md) 줄이기

상태: 대기 — 계획 확인 뒤 옮긴다

`CLAUDE.md` 가 너무 커서 세션마다 큰 비용을 낸다. 내용은 하나도 잃지 않고 '짧은 핵심 + 주제별 문서'로 나눠 줘. 먼저 계획만 보여 주고 사용자 확인 뒤에 옮긴다.

확인된 사실(2026-11-10):

- `CLAUDE.md` 는 305KB(238줄, 한 줄이 수 KB 짜리 문단)이고 `AGENTS.md` 는 제목 줄만 다른 사본이다. 세션 시작 때 지침과 메모리로 약 6만 3천 토큰이 들어가고 대부분이 `CLAUDE.md` 다.
- CI 의 check-agent-instructions 가 `scripts/check-agent-instructions-sync.sh` 로 두 파일을 대조한다(배포는 막지 않는다).
- 판정 관제실은 `CLAUDE.md` 의 `###` 소제목을 불변식 목록으로 읽는다(§7, `docs/CONTROL_ROOM.md`).
- 분량 대부분은 §4c 의 날짜별 점검 기록('화면 점검 N차' 등)이다. 불변식 대부분은 회귀 테스트 이름이 같이 적혀 있다.

원하는 것:

- `CLAUDE.md` 에는 빌드·테스트 명령, 작업 완료 기준, 불변식을 한두 줄 규칙으로(무엇을 되돌리면 안 되는지와 회귀 테스트 이름), 그리고 '이 영역을 고치기 전에 읽을 문서' 색인만 남긴다. 긴 경위는 `docs/` 아래 주제별 문서로 글자 그대로 옮긴다(요약하지 않는다).
- 짧은 규칙만 읽어도 그 불변식을 어기지 않을 수 있어야 한다. 자세한 문서는 '왜'를 위한 것이다.
- `###` 소제목 집합은 그대로 둔다. `AGENTS.md` 도 같은 구조로 맞추고 대조 스크립트가 계속 통과해야 한다.
- 잃은 것이 없음을 스크립트로 보인다: 옛 파일의 백틱 식별자, 테스트 이름, 날짜가 새 파일들 어딘가에 전부 있는지.
- 목표는 세션 시작 토큰을 절반 이하로 줄이는 것이다. 계획에 예상 크기를 적어 줘.

주의: 문서만 바꾼다(코드와 테스트 동작 불변). 관제실 파서 테스트가 깨지면 파서가 아니라 문서 쪽을 맞춘다.
