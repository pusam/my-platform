  **즉시 배포 표시는 푸시의 마지막 커밋(`head_commit`)의 제목 줄(첫 줄)에 `[deploy-now]` 가 있을 때만**이다. 커밋 본문이나 앞선
  커밋, 문서에 그 문자열을 적어도 이제 무해하다. 대기열에 있던 실행이 더 새 푸시의 실행으로 바뀌면 표시도 **그 새 푸시의 마지막 커밋**
  것만 본다(앞 푸시의 표시는 사라진다). 수동 실행(Actions → CI/CD Pipeline → Run workflow, 브랜치 main)의 `deploy_now` 도 보류·기다림을
  건너뛴다 — 판정 잡이 실패해도 배포 잡 조건이 직접 연다.
- **늦게 닫는 날** — 스크립트의 `LATE_CLOSE_DAYS` 표(지금 2026-11-19 하나)에 있는 날은 보류가 16:49 까지다. 그 표는 달력
  (`MarketCalendarService.closesLate`)과 같아야 하고 `DeployWindowLateCloseTableTest` 가 대조한다 — 달력에 날짜를 넣으면 스크립트도 같이.
- **미뤄진 배포** — 평일 16:27·17:12 KST 일정 실행. `preflight` 잡이 서버 백엔드의 이미지 커밋 라벨을 3회까지 읽고(못 읽으면 실패 —
  배포하지 않는다), `scripts/deploy-pending.sh` 가 그 커밋..main 끝을 본다:
  - 같으면, 또는 사이 커밋이 **전부** GitHub 건너뛰기 표시(`[skip ci]`·`[ci skip]`·`[no ci]`·`[skip actions]`·`[actions skip]`)면 빌드부터
    건너뛴다(그 표시는 push 실행에만 적용돼, 표시를 단 문서·설정 커밋이 일정 실행으로 재시작되지 않게).
  - 표시 없는 커밋이 하나라도 밀려 있으면 테스트·빌드·배포(보류된 배포를 잊지 않는다). 직전 배포가 실패했어도 다시 시도한다.
  - 서버 커밋이 main 의 조상이 아니면 실패(빨강) — 무엇을 덮는지 모르는 채 배포하지 않는다.
  - 17:12 일정은 늦게 닫는 날 16:50 까지 보류된 배포를 받는다. 평소엔 '배포할 것 없음'으로 끝난다.
- **⚠ 옛 보류 실행을 Re-run 하지 말 것** — Re-run 은 그 실행의 커밋(옛 커밋)을 배포한다. 밀린 배포를 지금 내려면 Run workflow(main).
- **재시작 기록** — 부팅마다 `server_boot_log`(V74) 한 행(JVM 시작·완료 시각·컨테이너·커밋 `APP_REVISION`). 관제실 ⑨ '장중 재시작' 카드가

  지금 프로세스의 부팅이 기록에 없으면 큰 글자가 '확인 불가'다.

## 가드가 고장 나면 — 막는다

판정 표(`scripts/test-deploy-window.sh`·`scripts/test-deploy-pending.sh`)가 하나라도 틀리거나 판정 스크립트가 실패하면 그 잡이 빨갛게
끝나고 배포하지 않는다.

- 막는 쪽(채택): 장중 재시작은 그날을 표본 시작일에서 빼고 수집 회차를 끊는다 — 되돌릴 수 없다. 늦은 배포는 빨간 실행으로 보이고 고치면 된다.
- 통과시키는 쪽: 가드가 조용히 무력해진 채 장중 재시작이 다시 생길 수 있다 — 이 작업이 막으려던 바로 그 일이다.
- 급한 수정은 수동 실행 `deploy_now`(빌드 3개가 성공했고 main 일 때).

## 화면만 바뀐 푸시는 백엔드를 재시작하지 않게 (설계안만 — 구현 안 함)

- **판정 기준은 '서버에 떠 있는 커밋 ↔ main 끝' 사이의 변경**이어야 한다. 이번 푸시의 `before..after` 로 보면 보류·실패로 쌓인 백엔드 변경을
  놓친다. `preflight` 가 이미 서버 라벨을 읽고 전체 이력을 받으므로 거기서 `git diff --name-only <서버 커밋>..<main 끝>` 을 계산한다
  (일정 실행만이 아니라 push 실행에서도 서버 라벨을 읽게 바꿔야 한다).
- 변경이 전부 `frontend/**`·`docs/**`·`*.md` 이면 `backend_changed=false`. 그때 배포 잡은 dist 전송·nginx 재바인드만 하고 백엔드·파이썬 이미지
  빌드와 `--force-recreate` 를 건너뛴다. 장중 가드도 이 경우엔 적용할 필요가 없다(백엔드가 재시작하지 않는다) — 다만 nginx 재시작이
  짧게 끊기므로 판단은 사용자 몫이다.
- **'Verify deployed revision' 과 맞추기**: 백엔드 라벨은 그대로 옛 커밋이므로 `github.sha` 와 비교하면 실패한다. 둘로 나눠 확인한다 —
  ① 백엔드 라벨 = `preflight` 가 읽은 서버 커밋(바뀌지 않았어야 한다) ② 화면 커밋 = `github.sha` — 빌드 때 `frontend/dist/revision.txt` 에
  커밋을 써서 배포 뒤 대조.
- 위험: `frontend/` 가 아직 배포되지 않은 새 API 를 부르는 경우 — 판정이 백엔드 변경을 놓치면 화면이 깨진다. 그래서 경로 목록은 '허용 목록'
  (이것만 바뀌면 생략)으로 두고, 모르는 경로는 백엔드 변경으로 본다.
